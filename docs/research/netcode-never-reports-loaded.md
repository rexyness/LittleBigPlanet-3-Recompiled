# Can a game take part in a join and never report the game state loaded?

Research for the [online co-op netcode map](../../.scratch/netcode/map.md), ticket 28. Written 2026-11-16. It builds on [How long can a joining guest that hangs keep everyone from stepping?](netcode-hung-join-blocks-all.md), answers its open question 2, and corrects one point of it and one of [What stops the host's simulation when a guest starts to join?](netcode-join-start-stall.md).

## Summary

- **Yes, by one road: a resource the joining guest is waiting for goes quiet while the connection stays up.** The guest asks the host for the snapshot's resources over the game's own streams, and before it reports it also waits for every other high-priority load it has pending. The only limit on a player who was asked is 600 s without an answer, and every answer and every piece restarts it, an empty piece included. A fetch that gets no answer therefore holds every PC for at least ten minutes, and by the code for up to eight such rounds. Two ways a host could go quiet were seen in its sending code and not settled; no log has either.
- **A fetch that fails does not hang the session** (the guest's side is known, the effect on the host inferred). The failure path through `0x34caf0` puts the guest's old world back, shows a notice and starts the game's own "back to my Pod". The guest never reports "loaded", but it leaves, the host drops its entry, and everyone else is unblocked. The one exception is a guest whose old world counts as having unsaved changes: it gets a "leave?" dialog first, and the others wait until its player answers.
- **A fetch that fails does so in seconds.** A host that says "I don't have it" is asked up to eight times, then the game server is asked twice over HTTP, then the resource is marked failed. The port's HTTP layer answers each attempt within its WinHTTP timeouts, which is up to 30 s an attempt when the server is slow.
- **The second pass, for the data labels, can stall the same way and no other.** It fetches one more resource from the host by the same road. A failed label fetch is ignored and the PC reports anyway. The 10 s limit of that step does not cover the wait, which runs inside the message handler. In the Pod the message carries no labels, so no log has ever run this pass.
- **The port's layers can't cause the hang.** The peer link and the socket bridge carry the game's datagrams whole and don't read them, and the game puts keepalives and resource messages on the same stream of a connection, so the port can't pass one and hold the other. The HTTP layer ends every call in an answer or a failure; a slow server can add its timeouts to a block, once per resource that is waiting on it.
- **There is no honest upper limit in seconds.** An honest wait is about 0.8 s, five round trips and the state's size divided by the game's resource allowance: 12,288 bytes a second at the start, 6,144 at the floor with two players, 4,096 with three or four. One megabyte at the floor is 163 s. A watchdog in the port has to measure progress, not elapsed time: no new resource bytes sent to the waiting guest for some tens of seconds while the simulation byte is clear.

## The road the game state takes

The hash message names the state by resource descriptors; the bytes come over the resource system. This is what `0x236550` waits on, so it is set out first.

### The loop

- **known** `0x236550(list, count, depth)` reads each resource's state byte at `+0x45`. 4 or 5 is loaded, 6 and above is failed, 0 to 3 is pending. For a pending one in state 0 or 2 it asks again (`0x236a60`). It returns "all loaded" or "something failed" once nothing is pending, and "failed" when the game is quitting (`0x13ef0`) or when the byte at `eboot+0x12ec65d` is set (written only in `0x239de0`, which was not read).
- **known** Each pass, on the main thread: the platform callbacks `0x6fe00`, a short sleep, and `0x2361a0`. That call runs the main thread's share of loading (`0x238280`: it takes loaded bytes off the queue at `eboot+0x12ec7f8` and builds the resource, for at most 10 ms a pass) and then the presenter `0x236060`.
- **known** There is no time limit in the loop.
- **known** The third argument is the priority the resource is asked at; the handler passes 1. The resource system counts the loads in progress by priority (`0x235510`, `0x235660`: the counters at `eboot+0x12ec7f0` and `eboot+0x12ec7f4`, the second for priorities under 3).
- **known** There is a second loop of the same kind on the way to the report. After the world is built and before `0x34a000`, the handler calls `0x2362d0` with 1 (in `0x34af50`, after `0x421f40`). It repeats `0x2361a0` for as long as that call returns true, which is for as long as the count at `eboot+0x12ec7f4` is above 0, and stops only then or when the game is quitting. So the guest reports only when **no load of priority under 3 is in progress anywhere in the game**, not only the snapshot's. No time limit here either.
- **known** `0x4b36f0`, called between the first two waits, walks the world's dependencies (`0x4b3760`, `0x4b3400`). It pumps (`0x236060`, `0x2361a0`) between passes and ends when a pass adds nothing new; it does not wait for a load. `0x4b3760` was read for its calls only.

### Who moves a resource to "loaded" or "failed"

- **known** A request made in state 0 goes on the queue at `eboot+0x12ec808` (`0x236a60`, `0x236e46`). Five threads serve the queues, started in `0x239920` and named there: "ResLocateThread" (`0x238d40`), "main fast thread" and "main slow thread" (`0x2386b0`, `0x238d00`, both `0x2386f0`), "HTTP loading thread" (`0x2390d0`) and "respump thread" (`0x238220`).
- **known** The locate thread looks for the resource on this PC (`0x2a5710`). Found, it goes to a reading thread. Not found, `0x239010` decides:
  - a type whose kind is 2 (`0x23ab70`), or the byte at `[eboot+0x130d5d0]+0x1c0` clear: failed at once, error 9;
  - the transfer manager on (`[eboot+0x1315b18]` is 1) and more than one player in the session (`0x33efe0`): the queue at `eboot+0x12ec720`, which is the **peers**;
  - otherwise `0x2385a0`: the queue at `eboot+0x12ec820`, which is **HTTP**, or failed with error 8 when the descriptor has no hash.
- **inferred** So in a session every resource this PC lacks is asked of the other players first, and the game server only after they have failed. Basis: the order in `0x239010`. The snapshot is made in the host's memory at the join (`0x23cc40` in `0x348e50`), so the server can't have it.

### Asking a peer

The transfer manager is the object at `eboot+0x1315b18`. Its update `0x3994e0` runs from the presenter with the socket work (`0x236108`) and from the network update (`0x34ad13`).

- **known** `0x3995b0` takes one request off the peers' queue when one of eight download places is free (`+0xb8`, 0x108 bytes each) and starts it (`0x39a260`). `0x39a5f0` fills in up to four players to ask, from the session's connection list (`0x34a650`), in an order that carries a random number.
- **known** `0x929cf0` sends the request as a class 1 message (`0x37a710` with 1): kind 0, "how big is it", when the size is not known, else kind 2, "send me bytes from here to the end". Class 1 is the resource class of [What makes the game netcode cut its send budget, and does the peer link trigger it?](netcode-send-budget-cuts.md).
- **known** The asked PC reads class 1 messages in `0x399970` and answers in `0x39ad70`: kind 0 through `0x39b9d0` (kind 1 with the size, or kind 4 "I don't have it"), kind 2 through `0x39be10` (it opens the resource for sending, or kind 4). With all 32 sending places taken it answers kind 4 with reason 1 (`0x39b4f0`).
- **known** `0x39b9d0` sends **no answer at all** when it can't open a message to the asker (`0x37a710` returns 0, `0x39bc7e`). `0x37a710` fails only when `0x379bf0` finds no connection object with an address for that player.
- **known** The pieces go out from `0x399700`, at most 1,300 bytes each, paced by the allowance (the send-budget ticket). The asker takes them in `0x92a960` (kind 3), checks the whole against the hash when the last byte is in (`0x1ce00`; a mismatch is error 7) and hands the bytes to the loading queues.
- **known** The sender of a piece, `0x39b730`, reads from one of three sources. For the two kept in memory (source `-3` through `0x9bdc0`, `-2` through `0x911f10`, a table looked up by number) a failed read drops the message (`0x37aa10`) and returns 0: nothing is sent, nothing is said to the asker, and the sending place stays taken, so the same read is tried again on the next pass. For a file (`0x21ff10`) the piece is sent with however many bytes the read gave, which can be none.
- **known** Keepalives and resource messages share a queue: the keepalive sender `0x37cff0` opens its message with class 0, the resource code with class 1, and `0x37a710` sends both classes to the same stream of the connection object (`+0x80` or `+0x90`, by whether this PC is the host).

### The one timer

- **known** Each asked player has a stamp at `+0x30` of its entry in the download place. `0x92a3d0`, run on every update of the manager, drops a player whose stamp is armed and older than **600.0** (`eboot+0xeeaa14`; unarmed is -1.0, `eboot+0xeeaa10`). The clock is `0x1b3f0`: nanoseconds since its first call times 1e-9, so seconds.
- **known** The stamp is set when the size request goes out (in `0x929cf0`, the kind 0 branch), when the size answer comes (`0x92a730`) and **on every piece** (`0x92a960`, at its top, before it looks at the piece's offset or length). It is cleared when the player says "I don't have it" (`0x92ade0`).
- **inferred** So it is a limit on silence, not on the whole transfer: 600 s since that player last answered. A transfer that keeps moving, however slowly, never runs into it. And a piece with no bytes in it restarts the limit like any other, so a sender in the file branch above whose reads give nothing would hold the asker with no limit at all. Basis: the three places that stamp, and the order of the stamp and the length test in `0x92a960`.
- **known** A second player asked with kind 2 gets no stamp: the kind 2 branch of `0x929cf0` writes the range but not `+0x30`. With two players there is only the host, who was stamped by the size request, so this bears on three or more players only.
- **known** A dropped player is skipped for a while (`0x39a190`): 1.0 s after a timeout (`0x39a0d0`, `eboot+0xe7a3a0`), 10.0 s after it answered "busy" (`0x39a010`, `eboot+0xe7a39c`). When nobody is left to ask, `0x92a1f0` puts the request back on the peers' queue while a count at `+0x194` of the request is under 8 (`0x2a5bb0` with 8), and after that hands it to HTTP.
- **inferred** So a host that never answers costs 600 s a round and up to eight rounds, about 80 minutes, before the server is asked and the fetch fails. Basis: the chain above, read once; the count's steps between rounds were not traced one by one. Never run.

### The server, after the peers

- **known** The HTTP thread makes at most two attempts per resource (`0x2390d0`, the loop on `uVar13`), then marks it failed: error 8, or 10 for status 410, or 7 for a body that does not hash to its name. It has no timer of its own; it waits in the HTTP call.
- **known** The port answers that call from WinHTTP with timeouts of 10 s to resolve, 10 s to connect, 15 s to send and 30 s to receive (`http_online.cpp:93`), and reads the body in the same call (`:548..559`). A GET of `/r/<sha1>` that comes back 200 is checked against its name and its type and turned into a 404 when refused (`CheckDownload`, `:349`).
- **inferred** So one resource's HTTP fallback ends within about two minutes at worst, normally in two round trips, and for a snapshot it ends in "not found". The receive timeout is per read, so a body that trickles has no total limit; nothing suggests a server would do that. Basis: the two points above.
- **known** There is one HTTP thread and one queue, ordered by priority. A resource can wait behind other downloads.
- **observed** The server does let calls run into the timeout at times: two POSTs at the start of run rw1 ended with WinHTTP error 12002 on both PCs (`A\stderr_rw1.txt:1292`, `:1293`; `B\stderr_rw1.txt:1218`, `:1219`).
- **inferred** Because of `0x2362d0`, HTTP loads of priority under 3 that are still open when the guest has built its world also hold its report, each for its two attempts at most. With a server that is not answering that is up to a minute per resource in the queue, with the guest's keepalives going and every PC waiting. Which loads a joining guest has open over HTTP at that point, and at what priority, was not read. Basis: the loop and the timeouts.

## (1) Whether the fetch can stall without failing

**Yes, in one way: silence from the host on the resource stream. At least 600 s, by the code up to about 80 minutes, and without limit if the host sends empty pieces. Known for the limits; that a game can get there is inferred. Two possible causes are in the host's sending code; neither was shown to happen.**

- **known** While the guest sits in `0x236550` its presenter runs `0x3994e0` with the flag set, which runs the socket work and the keepalive (`0x3604a0`) and then the manager's own steps. The hung-join ticket left the conditions on the way unread; they are: the main thread, the resource system started (`eboot+0x12ec658`, set to 1 in `0x239920`), the byte at `eboot+0x13a559c` clear (written only by the loading layer's draw `0x5173f0`), `0x670570` false (a count at `eboot+0x13aff60` not above 0), and the manager on.
- **inferred** If one of those conditions fails on the guest, the fetch stalls and so do its keepalives, and the host removes it after 10 s. That is the hung-join ticket's case B, which ends. Basis: the fetch and the keepalive are pumped by the same call.
- **inferred** The stall that does not end is the other one: the guest's pump runs, its keepalives go out, and the host's answers stop. Then the only limit is the 600 s above. The host's entry for the guest stays, state 9 has no timeout, and every PC waits. Basis: the timer, and the hung-join ticket's case C.
- **known** What does not cause it:
  - A host without the resource answers "I don't have it" (kind 4). The guest asks again at once, up to eight times, then the server. That fails in seconds.
  - A host with all 32 sending places taken answers kind 4 with reason 1. The guest drops it for 10 s (`0x39a010`) and retries; eight tries, then the server.
  - Loss on the path. Class 1 goes on the game's acknowledged streams, which resend ([What does the game netcode tolerate, and which of its limits can be reached?](../../.scratch/netcode/issues/03-game-netcode-limits.md)). Loss slows the transfer; every piece that arrives restarts the 600 s.
  - A cut send budget. The allowance never goes under 4,096 bytes a second (`0x37b5e0`, the send-budget ticket), so pieces keep coming.
- **inferred** The same holds for the second loop, `0x2362d0`: any load of priority under 3 that stays in progress on the guest holds its report, by the same roads. Basis: "The loop".
- **not found** What would make a host go quiet on the resource stream alone. Candidates read and not settled:
  - a read that fails on the host in the middle of a transfer (`0x39b730`, above): silence for a resource kept in memory, empty pieces for a file. The snapshot is written to memory at each join; whether its entry can be freed or replaced while it is being sent, for one by a second join's snapshot, was not read. This is the candidate closest to a real session with three players;
  - the host's manager off while the guest's is on (`[eboot+0x1315b18]` is tested at the top of `0x3994e0`; its writers `0x35fc10` and `0xa6910` were not read);
  - `0x39b9d0` finding no connection object for the asker and dropping the request without an answer, which needs the two PCs to disagree about who is connected;
  - with three or more players, a second player asked with kind 2 and never stamped, who then leaves or goes quiet. Whether a player's leaving clears its entry in a download place (`0x399e10`, called from remove-player at `0x34ee60`) was not read.
- **known** The rejoin without a spawn is not this. Its stuck transfer is in another manager, at `eboot+0x12cc4e8`, with session messages 0x12 to 0x14 ([rejoin_no_spawn.md](../../.scratch/lbp3-port/coop/rejoin_no_spawn.md)), and it comes after the unblock.

## (2) What the failure path does to the wait

**It ends it for everyone else. The failing guest never reports, and leaves instead. Known for the code on the guest; that the leave reaches the host is inferred, with the menu's leave as support.**

- **known** `0x34af50` calls `0x34caf0` from four places (`0x34b933`, `0x34c4ca`, `0x34c50f`, `0x34c562`): when the world or the players' resources fail in `0x236550`, when `0x4b36f0` reports an error, and when one of the two extra resources a guest loads fails. All four go on to the handler's clean-up at `0x34b938` and return. They skip `0x34a000`, so **no "loaded" is sent**, and they skip the write at `0x34ba97` and `0x34c605`, so the byte at `+0x45` **stays 0**.
- **known** `0x34caf0` itself: it releases what was half loaded (`0x2378d0`), makes the world it held from before the join current again (`0x246cc0` with the old world, `0x25dfa0`, `0x259540`), builds a notice from one of the text keys it was given (with the host's name when there is one) and calls `0x34efa0` with reason 3.
- **known** `0x34efa0` with 3: it puts the notice up (`0x5279c0`), sets the party stage row to 0x15 (idle) and calls `0x3513d0` with 0, 0, 0. That clears a per-player value (`0x4c7630` writes -1.0 at `+0x98`), passes its gate (`0x26a340` is true only when one of those values is not -1.0), writes this PC's own ID as the game to be in (`+0xb8`, `+0xdc`), and calls `0x36ea60` with 3, or 0xb while the byte at `eboot+0x130d8f0` is 0 (checked in assembly, `0x351880..0x3518cc`).
- **known** `0x36ea60` asks `0x265060` whether the current level has unsaved changes. It can be true only when the world's field at `+0x108` is not 0. If true, it raises the dialog "This level has unsaved changes. Are you sure you want to leave?" and returns. If false, `0x36ecb0` starts stage row 3.
- **known** Row 3 of the table at `eboot+0xe1c990` is `2a 10 15 16 2b 2c 2d 14 1f 20 24 27 11 22 2f 18`. With the mode this call sets (`+0x244` is 0) stage 0x10 sends nothing while a host slot exists, and 0x15 and 0x16 do their work only when `+0x244` is not 0 and otherwise step on; 0x2b and 0x2c write this PC's own ID as the next holder of both slot roles, itself and host (`0x3ae8a0`, which writes `+0x1810` and `+0x1818`, not the current roles at `+0x1800` and `+0x1808`); 0x2d sends the new room on (`0x3af220`).
- **inferred** That row is "back to my own Pod", and it ends the connection to the old host: when the roles change, `0x3aeb80` calls remove-player on the PC that held the role (`0x3aef20`, kind 1), which sends the goodbye and ends the signaling connection (the hung-join ticket, "What a removal does to the wait"). Basis: the stages above; the step from 0x2d to `0x3aeb80` goes through the room record's handler `0x375550` and was not followed call by call.
- **observed** The menu's "Leave to my Pod" does end the connection from the leaving side: on 15 November the friend's game called TerminateConnection and the host got DEAD with TERMINATED_BY_PEER ([rejoin_no_spawn.md](../../.scratch/lbp3-port/coop/rejoin_no_spawn.md), connection 1). Whether the menu goes through the same row was not read.
- **inferred** So after a failed fetch the host loses the guest within a few frames and a trip, drops its entry, and sends the unblock to everyone left (`0x3a8180`). The standstill is the time the fetch took to fail. Basis: the chain above; no log.
- **inferred** The exception: a guest whose own world, the one put back, has unsaved changes. It sits in the dialog with its main loop running and its keepalives going, having reported nothing. The others wait for its player. Basis: `0x36ea60`. What the field at `+0x108` stands for (create mode is a guess), and whether the game lets a player join from such a level without saving first, were not read.
- **known** On the failing guest the byte at `+0x45` is 0 after the handler returns. What sets it again there was not followed; `0x350225` (CHANGE_LEVEL) and stage 0x36 are the known setters.

## (3) Whether the second pass can hang the same way

**The fetch in it can stall exactly as in (1). The wait in it can't be left hanging by a failure. Known from the code; no log has run it.**

- **known** `0x349df0` calls `0x3a5e30`, which calls `0x3a5d50` on **every** PC. Only the sending of UPDATE_DATA_LABELS (0x68) is the host's (`test sil, sil` at `0x3a5d5e`, checked in assembly). `0x3a5d50` then loops, presenting and running the network update (`0x34a760` with 2), until this game has handled a 0x68 itself (the byte at `+0x650` of the object from `0x4cab10`) or 10.0 s have passed (`eboot+0xe7a490`) or the game is quitting.
- **known** The handler `0x87a920` runs inside that network update. When the message carries labels (its first field is not 0) it loads the labels resource by its descriptor (`0x2373e0`, type 0x42), waits for it in `0x236550`, **ignores the result**, and goes into `0x34a000` with the labels' key: it reports 0x66 and waits for 0x67. When the message carries none it skips all of that.
- **inferred** So the 10 s does not bound this pass. The clock is only looked at between network updates, and the handler does not come back until the fetch and the wait are over. Basis: the nesting.
- **inferred** The fetch is the same road as the snapshot's: a guest does not have the host's labels resource and asks the host for it. It can stall on the same 600 s of silence and nothing else. A failed fetch costs nothing: the PC reports anyway. Basis: `0x87a920` and the section above.
- **known** The wait ends on the host's 0x67 for the labels' key, sent when every slot that was at 9 or more when the host thread took the 0x68 has reported (`0x3a6640`, `0x3a8180`). By then every PC has been through the first wait, so all of them are running handlers.
- **known** The host thread makes its entries whether the message carries labels or not (`0x3a6640` does not look at the count), while a game reports only when it does. Entries for a message without labels are never reported and stay in the map until their slot goes. They belong to their own key, so they hold nobody. The key carries a number from `0x1b0d0`, so two such messages don't share one.
- **observed** In the Pod the message carries no labels: `e8 00 00 42 80 e1 d1 86 02`, 9 bytes, both joins of rm1 (`A\stderr_rm1.txt:4712`, `:12887`; `B\stderr_rm1.txt:13670`, `:22075`). Each log has two `67 12` lines, one per join, and none after an `e8`. So no run so far has made the second pass.
- **inferred** A PC whose 10 s run out before its 0x68 arrives goes on: it sets its state for the host to 0xb and the byte at `+0x45`, and takes the message later from the main loop, where the handler waits the same way. A guest can't step ahead meanwhile, since it steps on the host's frames. Basis: `0x349df0` after `0x3a5e30`.

## (4) What would have to go wrong, and whether the port could cause it

| Way | What it needs | Ends by | Could the port's layers cause it? |
|---|---|---|---|
| Host silent on the resource stream, connection up (snapshot or labels) | not found; a failed read on the host is the candidate, see (1) | 600 s a round, up to eight rounds; nothing, if empty pieces keep coming | no, see below |
| Another high-priority load still open on the guest (`0x2362d0`) | a resource asked of a peer or of the server that does not finish | as the row above for a peer; the HTTP timeouts for the server | only by the length of its HTTP timeouts |
| Guest's own pump stopped | a condition of `0x236060` false, or a freeze | the 10 s kick | not by the link; a freeze is the port's shader builds, as in the hung-join ticket |
| Fetch fails: host lacks the resource | a snapshot the host no longer holds | seconds; the guest leaves | no |
| Fetch fails after the peers: server asked | all peers failed | two HTTP attempts; the guest leaves | it bounds it; see below |
| Failed fetch on a guest with an unsaved level | the dialog of `0x36ea60` | the player | no |
| "Loaded" not sent though the game waits | no host slot or no connection object (`0x3adb20`, `0x3adbf0`) | the wait's own exits | no |

- **known** `0x34a000` sends 0x66 only when `0x3adb20` gives a slot and `0x3adbf0` succeeds, and waits either way. `0x3adbf0` fails when there is no connection object for the host, or removes the host when more than 1 MB is queued on the stream (`0x3adbf0`, the test against `0x100001`).
- **inferred** Neither leaves a game waiting: without a connection to the host the loop's "at most one PC" exit holds, and a removed host is the "another host" exit. Basis: the exits of `0x34a000`.
- **known** A game that asked for the state has the host at 8 in its own table: `0x3adb90` raises it when 0x0a is sent. So the early return in `0x34af50` for a state under 8 (`0x34b04d`) can't catch the PC that asked.
- **inferred** The peer link (`p2p_link.*`) and the socket bridge (`net_offline.cpp`) can't cause the first row. They carry the game's datagrams whole and don't read them, and the game queues keepalives and resource messages on the same stream. For keepalives to pass and pieces not to, something would have to choose by content or by size. The link's 1,200-byte figure only limits the copies it adds (`p2p_link.cpp:34`, `:319`), the bridge drops only when a socket has 256 datagrams queued (`net_offline.cpp:107`), and the game's reliability layer resends what is dropped. The largest datagram seen in a join was 317 bytes (the join-start ticket). Basis: those places; no run with a large state.
- **inferred** The HTTP layer (`http_online.cpp`) can't cause a stall without end. Each call returns within WinHTTP's timeouts, and what it returns for a snapshot is "not found", which is the failure path of (2). What it can do is lengthen a block by those timeouts when the server is slow, through `0x2362d0`. Shorter timeouts for `/r/` downloads during a join would cut that; whether it ever happens needs the log lines. Basis: "The server, after the peers".
- **known** The port's check of downloads (`CheckDownload`) applies to HTTP only. A resource that comes from a peer goes through `0x92a960`, which checks the hash and nothing else. That is outside this ticket; it is listed as a question below.

## (5) The longest honest wait

**No fixed number. Size over allowance, and the size was not found.**

- **inferred** An honest wait is about 0.8 s + 5 round trips + (bytes the guest must fetch) ÷ (the host's allowance toward it). Basis: the join-start ticket for the first two terms, the send-budget ticket for the third.
- **known** The allowance is the send budget less a reserve that grows with the players (0, 4,096, 8,192, 12,288), and never under 4,096 (`0x37b5e0`). With two players: 12,288 bytes a second at the starting budget, 6,144 at the floor. With three or four at the floor: 4,096. It is halved while a timer of the connection manager is under a second old (the send-budget ticket).
- **inferred** So at the floor 100 KB takes 16 s with two players and 24 s with three; 1 MB takes 163 s and 256 s. Basis: the table in the send-budget ticket.
- **observed** The guest received 119 game datagrams in the 5 s that hold the first join's block (`B\stderr_rm1.txt:14059`), and 254 in the next 5 s.
- **inferred** So the Pod's state is small: at the 317 bytes of the largest datagram seen in another run's join (the join-start ticket, run d3) that is under 38 KB for everything in the window. Basis: two runs put together; rm1 does not log datagram sizes.
- **not found** The size for a real level: the world, the players' own resources, and whatever the level refers to that the guest lacks, all of which `0x34af50` waits for. All logged joins were in the Pod.
- **inferred** What a watchdog needs is therefore progress, not a clock on the whole wait. The game's own rule is "600 s without a byte from this player". The port can hold a far shorter one, because a transfer that is alive delivers a piece at least every second even at the floor (4,096 ÷ 1,300 is three pieces a second, 1.5 when halved), and because 10 s of full silence already ends the connection by the game's kick. Something like: the simulation byte clear, the host's entry for a PC not reported, and no resource byte sent to that PC for 30 s. Basis: the rates above; the figure of 30 s is a proposal with no measurement behind it.
- **known** The state a watchdog would read, besides what the hung-join ticket lists. On the host, where it would act: the 32 sending places at `eboot+0x1315b18` + 0x8f8 + n × 0x618, each with the resource's hash at `+0x0`, the asker's ID at `+0xc8`, the start at `+0xec`, the length at `+0xf0` and the bytes sent at `+0xf4` (`0x39be10`, `0x39b730`). On the guest: the eight download places at `eboot+0x1315b18` + 0xb8 + n × 0x108, each with the request at `+0x10`, the size at `+0x8` and the bytes received so far at `+0x100`; each asked player's entry starts at `+0x1c` + m × 0x38 with its stamp at `+0x30`.
- **inferred** "Bytes sent" not moving is the test that also catches the empty pieces of (1). Basis: `0x39b730` adds the read's length to `+0xf4`.

## What a later pass needs to settle

Not found, listed in the sections above: any cause shown to happen for a host that stays connected and stops answering resource requests; whether a resource kept in memory can go away while it is being sent; which loads a joining guest has open at priority under 3 when it reaches `0x2362d0`; the writers of the transfer manager's "on" flag; whether a leaving player is cleared out of a download place; the calls between stage 0x2d and the removal of the old host; whether the menu's "Leave to my Pod" is row 3; what sets `+0x45` again on a guest whose join failed; whether a player can start a join from a level with unsaved changes; the size of a real level's state; any log of a failed fetch, a stalled fetch or a label pass.

Corrections to earlier findings:

- [How long can a joining guest that hangs keep everyone from stepping?](netcode-hung-join-blocks-all.md), case C: "when `0x236550` does report a failure the handler builds an empty world through `0x34caf0`". It puts the previous world back, shows a notice and leaves the session. It does not report "loaded".
- The same, case C: "whether the resource system gives up on its own was not read". It does, after 600 s without an answer from a player, and it then tries again up to eight times before it asks the server.
- The same, case C, names the snapshot's fetch as the wait before the report. There is a second one, `0x2362d0`, which waits for every load of priority under 3 on that PC.
- [What stops the host's simulation when a guest starts to join?](netcode-join-start-stall.md), step 8: "The host's game sends UPDATE_DATA_LABELS and loops in `0x3a5d50` … for at most 10.0 s". Every PC runs that loop; only the sending is the host's. And the 10 s does not cover a handler that is waiting inside it.

Questions this raises for the map:

1. **Does a join into a real level stay inside what the players will sit through?** The block is the state's size over an allowance of 4,096 to 12,288 bytes a second. It needs one two-instance join into a level with the session log lines on: the bytes fetched and the block's length. This is the join-start ticket's question 3 with the formula now known.
2. **Should the port's watchdog be "no resource byte for N s during a block"?** It is the only rule found that tells a slow honest join from a dead one. It needs the size measurement first, and a decision on N.
3. **Does a failed fetch end the block as the code says?** A run in which the host is made to answer "I don't have it" can't be set up from outside the game; the nearest test is a guest whose HTTP is cut and whose peer queue is skipped, which is not a real case. It may be enough to leave this as read.
4. **Resources that come from another player are not checked by the port.** `CheckDownload` refuses scripts and types only mods make when they come over HTTP. In a session the game asks the other players first, and that road has only the game's hash check. Whether that matters is a question for the joining-and-leaving lane and the user, not for the netcode.
5. **Can the host's snapshot go away while a guest is still fetching it?** A second join, or a rejoin, makes a new one. If the old one's bytes are freed, the first guest's transfer goes silent and nothing ends its wait for ten minutes or more. It is a read of `0x23cc40` and of who frees the in-memory table of `0x911f10`, and it bears on the three-player run.
6. **With three or more players, a second player asked for bytes is never timed.** If that player leaves in the middle of a transfer, nothing in the download place's own code drops it. Whether remove-player clears it is the missing read; the three-player run should include a leave during a join.
