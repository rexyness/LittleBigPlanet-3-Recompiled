# Can LBP3 render at 1440p ("2k")? (2026-11-12)

The human asked "can we run the game at 2k?". Both monitors are 2560x1440. Today the game renders at 1920x1080, registers two 1920x1080 display buffers, and the port's presenter stretches them to the window (`SDL_RenderTexture`, linear filter).

Static analysis only (the human was playing). Labels:
- **[dec]**: decompiled from the eboot (Ghidra; `tools/ghidra_decomp.sh`, `tools/ghidra_probe.sh`).
- **[dump]**: from logs and dumps (`analysis\fg_dump\bk_b_trace.txt`, one traced Bunkum frame; the shader cache `user\shader_cache\CUSA00473`, 1,635 translated shaders; `analysis\shaders\dumps`, 209 guest binaries).
- **[code]**: our runtime or shadPS4 source.
- **[inf]**: inferred.

## Verdict

**True 1440p rendering looks feasible, and it isn't one switch.** The engine is the PS3 renderer (`RendererPS3.cpp`, `gfxcore.cpp` in the eboot's asserts) with the PS4 resolution hard-coded in a handful of places:
- one global, which about 20 functions already follow;
- one table of render-target declarations with immediates;
- 4 more functions with immediates or float constants;
- about 17 shaders with 1080p literals baked in (SMAA and the composite).

That's roughly 80 byte patches in 7 functions plus a shader-literal substitution: about 3–5 days with the experiment below, at medium-high risk. The unknowns are the in-world UI placement, unseen shaders, and memory.

**The cheap win comes first:** FSR 1 (EASU + RCAS) is already vendored and built in our shadPS4 tree. Running it on the Vulkan side before the readback gives a sharp 1440p image from the 1080p render for about 1 day of work at low risk.

## 1. Where the resolution is decided

There is no `sceVideoOutGetResolutionStatus` import, and the game asks the system for nothing [dec]. Two mechanisms exist side by side:

**A. One global, set once** [dec]. In `FUN_0005bed0` (gfxcore init):
- `DAT_01202b38 = 0x780` (1920), `DAT_01202b3c = 0x438` (1080), `DAT_01202b58 = 0x1e00` (the pitch in bytes);
- instruction sites: `0x5bf83`, `0x5bf90`, and the pitch store just after.

The same function sizes the two display buffers from the global (`FUN_00ad1a20(desc, w, h, …)`, `sceVideoOutSetBufferAttribute(…, w, h, w)`, allocation "LocalFrameBuf"). About 20 functions read the global [dec]:

| Function | Use |
|---|---|
| `0x5bed0`, `0x5d3e0`, `0x791130` | display buffers and a display-sized target descriptor |
| `0x270430`, `0x270470`, `0x270510`, `0x46d250` | viewports `FUN_00058a20(0, 0, w, h)` |
| `0x42c4b0`, `0x42deb0`, `0x430240` | texel-size shader constants `k / w`, `k / h` (`0x42c4b0` uses w/2, h/2) |
| `0x4be40`, `0x4c810`, `0x4cd20`, `0x4d7b0`, `0x4dc10`, `0x4e0d0`, `0x3bbe10` | screen-space and 2D placement (centring, NDC conversion) |
| `0x55a010`, `0x55c2e0`, `0x7e4480` | `width < 1280`: the low-res UI branch (PS3 720p heritage) |

**B. Hard-coded immediates** [dec]:
- **`FUN_00427940` (`RendererPS3.cpp`)** declares every render target through `FUN_00462b50(desc, w, h, fmt, …)`:
  - 19 targets at 1920x1080 (3 of them depth: `0x133da08`, `0x133db40`, `0x133dba8`);
  - 2 at 1920x2160 (`0x133e430`, `0x133e9e0`, two 1080 halves stacked);
  - 2 at 480x270 (1/16 area);
  - a fixed bloom chain at 1280x720, 640x360 and 320x180;
  - resolution-independent shadow and atlas targets: 4096², 2048², 1024², 160x4096, 128x16384, and the 3D 256x128x64, 128x64x64 and 512x256x64 volumes.
- **`FUN_00424790` and `FUN_00426dc0`** each build a 1920x1080 colour+depth pair with immediates (`MOV ESI,0x780 / MOV EDX,0x438`, pitch `0x1e00`, word stores `0x780/0x438`). `0x424790` also divides by float constants 1920.0 and 1080.0 at `0xe811f4`/`0xe811fc`, which only it reads.
- **`FUN_00433880`** snaps to a 1920/1080 grid (floats at `0xe8235c`/`0xe82360`, read only there).
- **`FUN_006cd050`** projects NDC to 1920x1080 pixels (`(x + 1) * 1920 * 0.5`, floats at `0xe9fdc8`/`0xe9fdcc`, read only there). It is probably a screen-anchoring helper [inf].
- **Not resolution:**
  - `FUN_00074f20`/`0x75540`: 0x780 is a dispatch chunk size.
  - `0x3f6xxx`: 0x780-byte buffers.
  - `0x54d4f0`: an allocation size.
  - `0x512b00`: draws a fixed 1280x720 offscreen view (photo or thumbnail [inf]).
  - `0x6164b0`: a script switch whose case labels happen to be 0x10e/0x1e0/0x21c/0x2d0.

The traced frame confirms the set [dump]:
- 1920x1080: 12 colour targets and 4 depth targets;
- 480x270: 2;
- 2048x2048 depth: the shadow map;
- 1024² RGBA16F: 2;
- 512x256 RGBA8: 16 slices of the 3D volumes;
- the SMAA AreaTex (160x560) and SearchTex (64x16).

## 2. Allocation and memory

- **Sizes are computed, not a fixed map** [dec]. `FUN_00462b50` runs the Gnm-style init for each declared size and accumulates aligned offsets in two pools. `FUN_004626a0` then allocates one block per pool ("LocalRenderTargets", "MainRenderTargets") of the summed size. Bigger declarations grow the blocks by themselves, so no relayout is needed.
  - Two 1920x1080 targets (`0x133e0f0`, `0x133e978`) reserve at least 64 MB each (`param_7 = 0x4000000`); at 1440p they still fit inside that reservation.
- **Budget** [dec + log]:
  - The game maps Garlic 1,698 MB (`0x6a200000`, immediate in `0x5bed0`) and Onion 784 MB of the 5,056 MB the runtime reports (`kernel_memory.cpp`; play log `[kernel] map direct 'Garlic'…`).
  - At 1440p the scaled targets grow by about 140 MB (17 colour × 8.4 → 14.7 MB, 3 depth+stencil, 2 × 1920x2160), plus about 13 MB for the display buffers [inf, from the declarations].
  - Whether Garlic has that much free is unknown. If not, raise `0x6a200000` (2.5 GB of direct memory is unused).

## 3. Resolution baked into shaders [dump]

Scanning the 1,635 translated shaders for 1080p-derived float literals (1920, 1080, 1/1920, 1/1080, 2/1920, 1/960, 1/540, 480, 270, 1/480 and similar) finds **17 shaders**. In the traced frame:
- **SMAA:** `ps 3a0615bd`/`vs c9311bbd` (they sample AreaTex 160x560), plus the `0b2a3346`, `2949baf9` and `8e1db4f9` passes. All carry `1/1920`, `1/1080`, `1920` and `1080`: SMAA's `RT_METRICS` compiled in.
- **The composite `ps 5ed16706`:** `1/480`, the 480x270 bloom texel.
- **`ps 33c89263`** (into `17a018000`): `480`/`270`.
- **Not in the traced frame:** 8 more.

Other passes take texel sizes from constants computed from the global (`0x42c4b0`, `0x42deb0`, `0x430240`) [dec], so they follow by themselves. The guest-binary dump (209 shaders, covering 44 of the 114 in a level frame) agrees: 7–10 hits.

- **Fix:** substitute those literals when shadPS4 translates the listed hashes (1/1920 → 1/2560 and so on). Our recompiler controls the translation, so the game files stay untouched.
- **Risk:** levels not yet cached may hold more such shaders [inf].

## 4. UI and HUD

There's partial evidence and no verdict:
- 2D and screen-space placement reads the global (`0x4c810`/`0x4cd20` centre with `(W − w·s)·0.5`; `0x4d7b0`, `0x4dc10` and `0x4e0d0` convert with W and H) [dec].
- The engine has a resolution-aware branch (`width < 1280` → low-res UI assets) and reflection fields `m_screenMinBounds` and `m_oneOverScreenScale` [dec + strings].
- But `0x6cd050` and `0x433880` use fixed 1920/1080 floats [dec], so some anchoring is in 1080p virtual pixels.

**Expected** [inf]: the HUD scales or anchors correctly, and the parts using `0x6cd050`/`0x433880` (in-world labels, cursor snapping) sit off by 4/3 until those constants are patched. The experiment decides.

## 5. Higher-resolution or PS4 Pro paths

None.
- There's no `sceKernelIsNeoMode` import, and no 4K, checkerboard or dynamic-resolution strings [dec].
- The PSN metadata says `neoEnable 0`.
- The only alternate resolution path is the PS3-era low-res UI branch.
- `sceVideoOutGetDeviceCapabilityInfo_` bit 2 is stored at `0x120ac60` (not the PAL byte `0x120ac62`) and is unrelated to size [dec].

## 6. The runtime and shadPS4

- **shadPS4** has no internal-resolution scaling, but it does have **FSR 1** as a host pass:
  - `video_core/host_passes/fsr_pass.{h,cpp}`, `host_shaders/fsr.comp`, `fsr/ffx_fsr1.h` (AMD, MIT, already built from source);
  - used by its own `vk_presenter`, which our port bypasses [code].
- **The runtime can't simply report a bigger display:** the game doesn't ask [dec]. It must be patched, which the existing env-gated patch table (`core/patches.cpp`: expect/replace bytes, skipped if they differ) supports.
- **The runtime's own 1080p assumptions** [code]:
  - frame generation and capture: `fg_live.cpp` velocity-size check `>= 1920*1080*4` (fine), and **`renderer.cpp:612` `kSlot = 1920*1088*4`**, which must grow or the copies would overflow;
  - `libScePad` and `gamepad_sdl` touch resolution 1920 (pad space, unrelated);
  - the OSK and dialog overlays scale by window/1920 (window space, fine).

## 7. Frame generation at 1440p

- The game's vectors are in UV units: lane A's 0.941 px × 0.529 px per step equals the same UV step on both axes (0.941/1920 = 0.529/1080). So at 1440p the per-step pixel scale becomes 1.255 × 0.706, and the warp's `motionScale` must be multiplied by 4/3 [dump + inf].
- The hooks find the velocity and depth targets by role and size; they need the 2560x1440 sizes and the bigger `kSlot` [code].
- The warp costs about 1.78× more GPU (about 2.8 ms instead of 1.6) [inf].

## Cost at 1440p

[inf]
- The GPU phase is 4.5–5.2 ms at 1080p in Needlepoint; pixel-bound passes would make that about 8–9 ms.
- The display readback goes from 8.3 to 14.7 MB a frame (about +0.6 ms each).
- Everything stays well inside the 33 ms budget, with or without frame generation.

## Cheapest experiment (when the game is free, about 1–2 h)

1. An env-gated patch set `LBP3_RES=1440` in `core/patches.cpp`, all same-length imm32/imm16 edits:
   - the global init `0x5bf83`/`0x5bf90` and the pitch: 0x780 → 0xA00, 0x438 → 0x5A0, 0x1e00 → 0x2800;
   - the 1920x1080, 1920x2160 and 480x270 declarations in `0x427940` (→ 2560x1440, 2560x2880, 640x360);
   - the immediates in `0x424790` and `0x426dc0`;
   - the six float constants at `0xe811f4`/`fc`, `0xe8235c`/`60` and `0xe9fdc8`/`cc`.
   Leave the shaders unpatched, frame generation off, and grow `kSlot`.
2. Boot to the Pod, then Needlepoint (`m5_np_route.sh` with `M5_EXE`), and take screenshots against 1080p.
3. Check the image fills the frame, the HUD and popit placement, the SMAA edges (expected slightly off until the literals are patched), the bloom alignment (the composite's 1/480), the photo test, memory (no allocation failure in Garlic), and the GPU time.
4. Then add the shader-literal substitution for the 17 hashes and re-check.

**What breaks first** [inf]:
- **A missed site:** a 1080p sub-rectangle in the corner or a stretched pass.
- **Placement through `0x6cd050`:** popit and in-world labels.
- **SMAA and bloom offsets.**
- **The 1920x2160 stacked targets,** if the second half's offset is computed from 1080 somewhere outside these functions.

## Fallback, and the first thing to build: a better upscaler

- **Where:** the Vulkan side, before the readback.
  - Run shadPS4's `FsrPass` (EASU upscale 1920x1080 → window size, then RCAS sharpening) on the display image.
  - With frame generation, run the generator at 1080p (native vectors) and upscale both the real and the generated frame.
  - The presenter then shows 2560x1440 one-to-one.
  - The SDL/D3D11 side is the worse place: SDL3's renderer has no custom-shader hook.
- **Cost** [inf]:
  - GPU: about 0.2–0.4 ms per presented frame on the 3090.
  - Readback: 14.7 MB instead of 8.3 MB.
  - Effort: about 1 day.
  - Risk: low, because it doesn't touch the game.
- **Our own Lanczos + sharpen compute shader** is also possible without external code, but FSR 1 is already in-tree and better suited.
- **Option for later:** temporal upscaling (FSR 2-style) would need jitter the game doesn't do (SMAA 1x), so it adds little.
