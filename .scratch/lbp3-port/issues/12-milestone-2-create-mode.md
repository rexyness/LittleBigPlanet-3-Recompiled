- 2026-11-11, **black photos found and fixed** ([m2/photo.md](../m2/photo.md)):
  - **Cause:** a photo renders the scene into three linear 32-bit targets (1280×720, 640×360, 320×180), and four frames later the game copies them out with a plain CPU memcpy (eboot `0x4014f0`), with no fence in between. The port kept the images on the GPU, so the copy read zeros. The encoder was fine. Capture Object, the level thumbnails and the profile's save icon read the same targets and were blank for the same reason.
  - **A/B:** `LBP3_READBACKS=relaxed` changes nothing, `precise` doesn't get past the boot in time, `LBP3_READBACK_IMAGES=1` gives the scene.
  - **Fix** (shadPS4 `50b4720a`, clone `dd67f93`, merged as `d534bbe`): linear 32-bit 2D colour targets are downloaded synchronously and written back, but only while the game's own "capture queued" byte (`eboot+0x132d699`, read by the job runner at `0x401a5a`) is set. The runtime checks that code at boot and logs if it differs. Without the gate a Bunkum cutscene's one-off 1920×2160 linear target took 118 ms to download.
  - **Cost:** 3 downloads per capture (at the Pod, when a level opens, on Save Changes, per photo). The first download waits for the GPU, 11–21 ms, so a photo frame takes about 41 ms. Nothing is downloaded in any other frame, and the status line now ends with "K read back".
  - **The save icon** goes from blank to a portrait whose channels look rotated. A static check showed this is the game's own doing: its PNG path turns on libpng's swap-alpha (A,R,G,B input) for a B,G,R,A buffer, while its JPEG and DXT paths read the same target as B,G,R,A. So the port writes what the game's code writes; nothing in the port displays that file.
